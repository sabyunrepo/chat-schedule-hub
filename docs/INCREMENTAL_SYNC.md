# 대시보드 증분 동기화

2026-11-01: 실제 개인 사이트에 일정 98개(카카오톡 카드 87, Google Calendar 10, 메일 검토 후보 1), 인물 1개, 수집 대상 20개를 반영했다. 자유형 대화 전체 일정 추출은 미완료다. 모집 공지는 내 참석 확정으로 취급하지 않으며 카드의 일정협의/일협은 시작 시각을 미정으로 남긴다.

## 계약

`hub.delta_sync`와 `/api/sync` schemaVersion 2를 사용한다. 전체 스냅샷 교체는 더 이상 받지 않는다. 구버전 수집기는 갱신해야 한다.

- DB/목적지별 installation UUID와 증가 sequence를 로컬 SQLite에 유지한다.
- 일정·인물·소스별 마지막 승인 지문과 비교하여 변경분만 전송한다. 한 요청은 최대 200개. 변경 없음은 HTTP 요청 0회다.
- 로컬 현재 레코드 비교는 O(N), 지문 목록은 한 쿼리로 읽는다. 전체 재분석·전체 업로드·서버 전체 레코드 재작성은 하지 않는다. 대규모 데이터에서는 로컬 변경 로그를 통한 dirty-key 조회와 목록 API 페이지네이션이 후속 최적화다.
- 전송 전에 정확한 pending 요청을 저장한다. 실패/종료 후 같은 요청을 재전송한다. 서버 승인 sequence를 확인한 뒤에만 지문·outbox 승인 상태를 갱신한다.
- 서버는 D1의 레코드별 UPSERT와 batch 원자성을 사용한다. 오래된 요청은 쓰지 않고 동일 sequence의 다른 본문은 충돌로 처리한다. owner+installation으로 수집 DB를 격리한다.
- 기존 snapshot은 마이그레이션에서 한 번만 레코드로 옮기고 원본 테이블도 보존한다. 필터·pairing은 그대로 유지한다.
- 목록에서 빠졌다는 이유로 삭제하지 않는다. 취소는 일정 상태 변경이다. 명시 삭제/보존 만료 프로토콜은 별도 후속 과제다.
- 여러 수집 DB의 ID는 원래 전역 namespace를 유지한다. 복제 DB의 installation을 초기화하여 중복 공급자로 보내지 않는다. 같은 ID를 여러 공급자가 소유하는 충돌은 운영하지 않는다.

## 실행

`HUB_DB`에 수집 DB를 지정하고 `python3 -m hub.cli sync`의 stdin에 `{"origin":"https://YOUR-SITE"}`를 전달한다. `HUB_SYNC_TOKEN`은 사이트 연결 키, `HUB_SITE_ACCESS_TOKEN`은 Sites 접근 토큰이다. 짧은 수명의 접근 토큰을 파일에 저장하거나 명령 인자로 넣지 않는다. 초기 설치 때 사이트에서 연결 키를 발급하고 개인 비밀 저장소에 보관한다.

새 데이터는 코드 재배포 없이 동기화한다. 조회 API는 현재 데이터를 읽으며 변경 시에만 DB 레코드가 갱신된다. 조회 응답 자체의 delta/ETag 전송은 아직 구현하지 않았다.

## 확인 결과

- 최초 전송: 카카오톡 103개 레코드, Discord 1개, 메일/Calendar 15개.
- 각 DB 즉시 재실행: 요청 0회, 레코드 0개.
- 일정협의 문구 보정: 카카오톡 일정 10개만 변경. 전체 일정 교체 없음.
- 테스트: 실패 재시도·동일 요청·목적지 격리·삭제 추론 금지, 마이그레이션 보존·서버 오래된 요청 차단·사용자 격리.

문제 시 동기화 실행을 중단한다. 기존 D1/로컬 DB를 삭제하지 않는다. schemaVersion 1 수집기로 되돌리면 현재 API가 409를 반환한다. 프로토콜 버전과 서버 버전을 함께 맞춘 후 재개한다.
