# Discord 봇 수집 전환 계획

상태: 앱 생성·토큰 안전 저장·공식 API 인증·두 서버 접근 확인. 제한 REST 파일럿을 공통 선별/저장에 연결해 실제 실행했다. Gateway 상시 수집·전체 30일 이력·수정 이벤트/복구 검증은 미완료이며 전체 확대는 보류다. 마지막 검증 절이 최신 상태다.

## 목표와 경계

- Python discord.py 기반 discord-bot SourceAdapter를 추가한다. 기존 Decisions/Store/일정/착오 검토/동기화 파이프라인을 재사용한다.
- 사용자 지정 두 서버만 allowlist로 허용한다. 실제 ID는 사용자 전용 설정에 둔다. 설치된 다른 서버의 이벤트는 저장·AI 전송 전에 거부한다.
- 첫 기간은 실행 시작 기준 최근 30일. 이후 신규 메시지, 수정, 명시 삭제, 채널·스레드 변경 이벤트로 증분 처리한다.
- 접근 가능한 텍스트/공지 채널, 포럼·미디어 게시물 스레드, 활성/보관 스레드, 지원되는 음성채널의 텍스트 이력을 범위에 포함한다. 통화 접속/녹음은 하지 않는다.
- 사용자와 봇의 접근 범위는 다르다. 비공개·권한 없는 채널/스레드는 미수집으로 표시한다. 이름을 아는 대상도 권한을 우회하지 않는다.

## 봇 생성과 권한

- 이름 후보: Moa Schedule Collector. 기존 동명 앱이 있으면 소유와 목적을 확인하여 중복 생성을 피한다.
- Guild Install, bot scope. 슬래시 명령 미사용 초기 버전은 applications.commands를 요구하지 않는다.
- 기본 권한: View Channels + Read Message History. Administrator, Send Messages, Manage Messages, Manage Threads, Connect/Speak는 요구하지 않는다.
- Gateway intents: guilds, guild_messages, message_content. 불필요한 members/presences는 끈다. Message Content는 포털 설정과 코드 양쪽을 확인한다.
- 비공개 스레드는 초대/허용 범위에서 수집한다. 이를 위해 관리 권한을 자동 확대하지 않는다.
- 토큰은 사용자 앱 데이터의 owner-only 파일 또는 OS 비밀 저장소에 보관한다. argv, 로그, Git, Sites, 플러그인 기본값에 넣지 않는다.
- 서버 설치는 Manage Server 등 설치 가능 권한이 있는 계정/관리자의 승인이 필요하다. 현재 사용자 권한은 실제 설치 화면에서 확인한다.

## 파이프라인

공식 이벤트/이력 → allowlist·권한 확인 → 대상/메시지 ID 대기열 → 공식 API로 필요한 본문 확보 → 내용 revision 비교 → 최소 문맥 구성 → Decisions → 가치 있는 근거 저장 → 일정/착오 후보 → 개인 사이트.

Codex가 모든 메시지 본문을 다시 읽어 정규화하지 않는다. 코드가 정규화하고 Codex에는 집계/오류/검토 후보를 반환한다. 봇 본문은 Decisions 판단에 필요하지만 영구 저장은 선별된 근거만 한다.

## 초기 수집과 실시간 병행

1. Gateway 연결과 대상 발견을 먼저 시작한다. 허용 서버별 권한·채널·활성 스레드를 조사한다.
2. 시작 상한 시각/ID와 30일 하한을 고정하고 과거 이력을 공식 페이지네이션으로 읽는다. 보관 스레드 목록은 별도 페이지 탐색한다.
3. 동시에 들어오는 실시간 이벤트는 대기열에 합친다. 대상별 ID/revision으로 초기 이력과 중복 제거한다.
4. 최초 범위와 새 메시지 범위의 진행 상태를 분리한다. 새 글을 읽었다고 과거 미완료 구간의 커서를 덮어쓰지 않는다.
5. 권한 오류, 빈 content, 미완료 보관 목록, 페이지 오류를 완료로 처리하지 않는다.

## 대기열과 장애 복구

- 로컬 SQLite 대기열은 기본적으로 서버/채널/메시지 ID, 작업종류, 수정시각, 재시도 시각만 저장한다. 미선별 본문을 영구 원문 로그로 남기지 않는다.
- 짧은 문맥과 연속 이벤트 병합은 제한된 메모리 버퍼에서 처리한다. 메시지별 중복 이벤트를 합치되 삭제/수정의 순서를 보존한다.
- 분석 실패 시 ID를 재시도하고 API로 현재 본문을 다시 가져온다. 그 사이 수정/삭제된 과거 본문은 복구 불가할 수 있으므로 공백을 표시한다. 원문 비보관의 명시적 한계다.
- SDK 재연결/Resume를 활용하고 세션 복원이 불가능하면 저장된 대상별 지점부터 이력을 재조회한다. 신규 after-ID만으로 과거 수정/삭제가 전부 복구된다고 주장하지 않는다.
- 최근 구간을 제한 재검사하고 목록/권한/보관 스레드는 더 낮은 빈도로 대조한다. 재확인 주기는 측정에 따라 조정한다.
- SDK rate-limit 처리와 제한된 동시성, 지수 backoff를 사용한다. UI 클립보드/메시지별 클릭은 사용하지 않는다.
- raw edit/delete 이벤트를 사용한다. 부분 수정 payload는 기존 revision 또는 재조회와 결합한다. embed-only 변경과 실제 본문 변경을 구분한다.

## 모델 비용

- 변경 없는 주기는 Decisions 0회. 같은 의미 revision과 같은 의존 문맥의 재전달도 0회.
- 페이지 전체 해시 대신 메시지 의미 revision + 실제 답글/사안 문맥 의존성 + 모델/프롬프트/보존규칙 버전으로 캐시한다. 관찰 도구·페이지 순서 변경은 내용 변경과 분리한다.
- 새/수정 메시지와 필요한 답글만 보낸다. 시간대/날짜/작성자 ID는 코드가 정규화한다. 모든 방의 내용을 매번 입력하지 않는다.
- 같은 방/스레드의 작은 묶음으로 전송하되 최대 개수/문자수/지연을 제한한다. 서로 무관한 방을 하나의 대화로 섞지 않는다.
- 관련성+의도 동시 질문과 관련성 우선의 2단계 방식을 실제 입력/질문 수·비용·누락률로 비교한다. 단지 호출 수가 적다는 이유로 저렴하다고 결정하지 않는다.
- 불확실 결과는 문맥 보완 큐로 보낸다. 무관 잡담은 본문 폐기, 비교 가능한 사실·정정·조건·시간·참여·필요한 답글은 보존한다.

## 데이터와 조회

- 안정 키는 source/connection/guild/channel/message. UI 파일럿 발생 키와 자동 병합하지 않고 검증된 매핑만 사용한다.
- 수집 커서, 분석 완료, 사이트 반영 완료를 분리한다. SQLite 배치 트랜잭션, 대상별 커서, 상태/재시도시각 인덱스, ID 기반 중복 제거를 사용한다.
- 필요한 사실은 claim + evidenceRevision으로 연결한다. 관심 사안/인물/시간 후보를 DB에서 좁힌 후 충돌 검토한다. 모든 메시지 쌍을 AI로 비교하지 않는다.
- 처리완료/의견/재열기 이력은 수집 데이터와 분리한다. 자동 재수집이 사람의 판단을 덮어쓰지 않는다.
- 봇 worker는 초기에는 Mac 로컬 프로세스로 운영한다. 절전 중 실시간 수집은 멈추며 재기동 복구가 필요하다. 상시 호스팅은 이후 별도 배포한다.

## 검증과 확대 순서

1. 어댑터·대기열·정규화 합성 검증: 신규/중복/수정/삭제/부분수정/실패재개/allowlist/권한변경/초기+실시간 경합.
2. 첫 서버 한 채널과 한 스레드의 최근 30일 이력을 API와 사용자 화면 표본으로 대조한다. 테스트 메시지를 무단 발송/수정/삭제하지 않는다.
3. 필수 일정/사실 표본 누락 0, 다른 메시지 오병합 0, 같은 입력 중복 저장 0, 미확인 구간 완료 처리 0을 수용 기준으로 둔다. 소규모 무누락이 전체 정확도 보장은 아니다.
4. 무변경/중복에서 모델 호출 0, 새 메시지 100개당 API 입력량·질문 수·총 지연·UI 개입 수를 기록한다. 실제 요금 정보가 없으면 비용을 추정으로 표시한다.
5. 통과하면 첫 서버 전체 접근 범위로 확대하고 이어 두 번째 서버를 수집한다. 실패한 유형은 보류하고 coverage에 표시한다.
6. 전체 완료는 최초 범위, 활성/보관 스레드 탐색, 권한 제외 목록, 미분석/미동기화 잔량까지 확인한 뒤 판정한다.

## 수정 메시지 수집 — 사용자 확정

- 신규뿐 아니라 이미 확인한 메시지의 수정도 수집한다. 채널의 마지막 신규 ID가 그대로여도 수정 이벤트를 처리한다.
- 최초 분류에서 제외한 메시지도 수정되면 다시 가져와 선별한다. 과거 제외 판정을 영구 적용하지 않는다.
- 기존 보관 메시지는 같은 원본 ID 아래 새로운 의미 revision으로 저장하고 이전 근거를 보존한다. 수정에 영향받는 일정/착오 검토 후보만 재분석한다.
- raw update의 content 필드 부재를 빈 본문으로 해석하지 않는다. 필요한 필드는 기존 관찰과 결합하거나 공식 API로 재조회한다.
- 본문/첨부/답글 등 의미가 같고 미리보기만 바뀌면 불필요한 Decisions 호출을 생략한다. 동일 수정 이벤트의 중복 전달은 멱등 처리한다.
- 연결 중 관찰한 수정과 오프라인 이후 재조회한 현재 상태를 구분한다. 접속 전에 있었거나 빠르게 연속 변경된 모든 중간 원문을 복구할 수 있다고 약속하지 않는다.

## DB 결정

로컬 SQLite + Sites D1을 유지한다. 별도 외부 DB는 추가하지 않는다. 역할, 현재 한계와 확대 조건은 [DB 설계 결정](DATABASE_DECISION.md)을 따른다.

## 포털 설정 확인

- 개인 설치 비활성화, Guild Install 활성화 및 View Channels/Read Message History 기본 권한 저장 확인.
- 기본 Guild Install scope에는 applications.commands가 아직 남아 있다. 별도로 생성한 설치용 URL은 bot scope만이며 permissions=66560이다. 기본 scope 정리는 후속 작업이다.
- OAuth 승인 페이지는 로딩 후 로그인 화면으로 이동했다. 이후 사용자가 공식 bot-only 링크로 두 서버 설치 완료를 알렸다. API 접근 검증은 토큰 연결 후 진행한다.
- 첫 봇 토큰 발급 제출 후 Discord가 비밀번호 재인증을 요구했다. 토큰 발급·저장·연결 완료를 아직 확인하지 못했다.
- 사용자 전용 로컬 설정에 앱 ID/허용 서버/30일 범위와 전체 수집 비활성 상태를 저장했다. 실제 ID와 비밀은 공개 문서에 포함하지 않는다.

## 실제 연결 및 제한 파일럿 결과

후속 검증으로 앞의 토큰/서버 연결 대기 상태를 해소했다. 사용자 재인증 후 토큰을 0600 파일에 저장하고 클립보드를 비웠다. 공식 API에서 봇 ID 일치 및 두 서버 접근을 확인했다. 채널 목록은 각각 10/4개, 활성 스레드는 5/2개다. 목록 수는 읽기 가능한 본문 수 또는 전체 이력 완료 수가 아니다.

- 첫 서버 한 채널: 최근 30일에 해당하는 1개 관찰/1개 보존. 채널 확인+본문 조회 764.78ms, Decisions 1644.27ms.
- 첫 서버 한 활성 스레드: 16개 관찰/9개 보존/7개 본문 제외. 채널 확인+본문 조회 666.82ms, Decisions 700.93ms.
- 동일 배치를 새 batchId로 재전달: 두 파일럿 모두 신규/수정 0, API 호출 0. 스레드 16개 cache hit.
- 관찰된 reply evidence gap 0. 이것은 선별 정확도·누락·전체 30일 완전성 검증을 대체하지 않는다. 원본 대화는 공개 보고에 넣지 않았다.
- 합성/회귀 테스트 34개 통과: 부분 수정 재조회 요구, 서버·채널 범위 차단, 수정 revision 이력, 중복, 낮은 관련성의 uncertain 보존 포함.
- 제한 REST 파일럿 런타임은 구현했다. Gateway 신규/수정 이벤트, 자동 과거 페이지 순회/보관 스레드, 재연결 복구, 실제 수정 이벤트 검증은 남아 있다. 따라서 전체 수집은 계속 보류한다.
- API/DB의 실제 연결을 확인했으나 일정 추출·Sites 동기화까지 완료한 결과는 아니다.
